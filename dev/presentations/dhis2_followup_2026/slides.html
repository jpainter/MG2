A Follow-up to the DHIS2 Annual Conference

Last time: a demo of what MG2 does.

This time: a developer conversation about a hard problem.

“DHIS2 is where the data lives — but what if the analysis it needs can’t be done inside DHIS2?”

Welcome and thank everyone for joining. Brief context: MG2 was presented at the annual conference with a demo and overview of what the app does. The videos from that are available. Today is a deeper conversation — specifically about one design challenge we haven’t solved yet, and we want the group’s input. This is not a product pitch, it’s a genuine design discussion.

Why Build Outside DHIS2?

What DHIS2 analytics can do

  • Calculated indicators (ratios, rates)
  • Predictors (moving averages, regression)
  • Validation rules
  • Built-in visualizations and dashboards

What epidemiologists actually need

  • Time-series decomposition (trend + seasonal)
  • Multiple outlier detection algorithms
  • Reporting-bias adjustment
  • Ensemble forecast models (ETS, ARIMA, MASE)
  • Burden estimation with statistical uncertainty
  • Climate covariates

R’s fable / feasts ecosystem — and Python’s statsmodels, prophet, scikit-learn — provide these. They are not replicable in JavaScript or Java analytics engines.

The tension: the richer the analysis, the further you are from where data lives and where users expect to see results.

This isn’t a criticism of DHIS2 — DHIS2 does what it’s designed for very well. But there’s a class of epidemiological analysis that requires a full statistical computing environment. R and Python exist for exactly this reason. The question isn’t whether to use them — it’s what happens to the results once the analysis is done.

What MG2 Produces

A typical analysis session generates outputs across multiple domains:

Data quality

  • Reporting completeness rates (facility × month)
  • Outlier flags — 6 sequential algorithms
  • MASE stability scores

Adjusted estimates

  • Reporting-bias-adjusted case counts
  • Trend estimates (time-series decomposition)

Modeling

  • Forecast medians + prediction intervals
  • WPE intervention effect estimates

Burden

  • Subnational burden estimates (5 methods)
  • Statistical uncertainty ranges

Climate

  • Monthly rainfall by org unit (CHIRPS)

~10 output types, some with multiple parameter variants. Keep this inventory in mind — we will return to it.

Walk through the output types briefly. The key point is diversity — these are not all the same kind of thing. Reporting completeness is a percentage. An outlier flag is a boolean with a reason. A forecast is a distribution. A WPE effect is a unitless ratio. A burden estimate has 5 methodological variants. This diversity matters for what comes next.

“The person who needs the output is not the person running the analysis.”

This is the core problem. The analyst does sophisticated work — runs models, explores parameters, compares methods. But the people who should act on those results — district health officers, program managers — have no window into the analysis. Results live in the analyst’s R session and local files. Fine for exploration; unworkable for routine programmatic use.

This 2x2 frames the entire conversation. SNT (Sub-National Tailoring — the MACEPA/PATH workflow) is analyst-only and outputs documents. CHAP elegantly solves the bottom-left quadrant: small number of well-defined forecasts pushed back to DHIS2. The bottom-right — rich, diverse analytical outputs visible in DHIS2 — nobody has solved this yet. That’s what we’re working toward.

Architectural Options

Option Results live in Pro Con
A Keep in app External session / files No DHIS2 config needed; fast iteration Invisible to standard users
B Push to source instance Original production DHIS2 Users already have access; existing dashboards Namespace risk; data element governance burden
B+ Aggregate Data Exchange API Source or separate (v2.39+) Reusable configs; scheduled jobs; cross-instance auth Pre-created data elements still required
C Separate output instance New DHIS2 (local or hosted) Clean separation; full DHIS2 API Second system to maintain
D Non-DHIS2 store PostgreSQL + Superset / Grafana Maximum flexibility Leaves the DHIS2 ecosystem

No single right answer — context determines the choice. MG2 is currently prototyping Option C.

The Aggregate Data Exchange API (/api/aggregateDataExchanges, v2.39+) is worth knowing — a higher-level primitive than raw dataValueSets for systematic cross-instance pushes.

Walk through each option. Emphasize B+ — the Aggregate Data Exchange API is relatively new and the audience may not all know it. It defines reusable exchange configurations with scheduled jobs and cross-instance PAT authentication — better infrastructure than calling dataValueSets directly if you’re going to do this repeatedly. But it still requires pre-creating data elements, which is the fundamental governance challenge.

CHAP: A Reference Model

Architecture

DHIS2 instance
  └── Modeling App (React)
        ↕ Route API
CHAP Core (Docker Compose)
  ├── FastAPI (port 8000)
  ├── PostgreSQL (models, predictions)
  ├── Redis + Celery (async jobs)
  └── Model sidecars (MLproject)

Fixed output schema

5 quantile bands: 10th · 25th · 50th · 75th · 90th + optional outbreak alert flag

How the push back works

  1. User runs prediction
  2. Opens “Import prediction” form
  3. Selects 5 pre-existing DHIS2 data elements — one per quantile band (CHAP does not create them)
  4. Dry-run validation
  5. Optional clear of ±12-month window
  6. POST /api/dataValueSets

Gotcha: the ±12-month clear can silently overwrite legitimate data if data elements are shared for other purposes.

Within its scope, this is elegant. For forecasting one disease with one model shape, 5 quantile bands is exactly right. The simplicity is a deliberate feature, not a limitation.

CHAP is a genuine success story in this space — University of Oslo / HISP, Wellcome funded, AGPL-3 licensed. The key architectural insight is that they constrained the output schema aggressively. By deciding that “a forecast” always means 5 quantile bands, they made the DHIS2 integration tractable. The admin creates 5 data elements once and the system runs from there. This is the right design for climate-informed disease forecasting. The question is whether it generalizes.

The “Many Outputs” Problem

Does CHAP’s fixed-schema approach scale to richer analysis?

Output type DHIS2 representation The problem
Adjusted case count NUMBER, SUM Straightforward — the easy case
Forecast median NUMBER, AVERAGE Which model? Which parameters?
Outlier flag BOOLEAN or NUMBER Loses the reason: algorithm, threshold
WPE effect size NUMBER, AVERAGE Unitless — meaningless without model context
Reporting rate Two data elements + indicator Numerator and denominator must travel together
Burden estimate NUMBER × 5 methods Which estimate does the health officer look at?

Root cause: DHIS2 data elements are optimized for data entry, not model metadata. No concept of provenance, version, or parameter set.

Open question for this group: Is there a DHIS2 metadata pattern — attribute option combos, data store API, custom attributes — that could carry provenance alongside values?

This is the hardest slide intellectually, and the one where the audience’s expertise is most valuable. Outlier flags are not measurements — they are analyst judgments with associated reasons. A WPE effect size without knowing which model was run and over what period is ambiguous. Burden estimates exist in 5 methodologically distinct variants. If you push all of this to DHIS2 you end up with dozens or hundreds of data elements and a governance problem. The DHIS2 data store API is one possible escape hatch — it can store arbitrary JSON per org unit / period — but it’s not queryable via the analytics engine. I want to know if the developers in the room have seen this problem before.

What We Built: The Output Tab

A four-step pipeline — Steps 1–3 functional today, Step 4 in progress:

1
Source info
Read from metadata — system name, version, org unit count, data elements. No connection to source needed.
2
Spin up local DHIS2
d2 cluster up at matching source version; polls until ready; structured error UI for missing docker-compose, d2 CLI, Docker daemon.
3
Import metadata
Org units (batched) + data elements derived from loaded formula (nothing hardcoded) + 4 fixed MG2 output elements.
4
Write values
Raw data via dataValueSets API (batches of 2000) ✓  |  Model outputs — in progress ⚙

Key design choice

Data elements in Step 3 are derived entirely from whatever formula the analyst loaded — nothing is hardcoded. The output instance mirrors the current dataset.

Contrast with CHAP: admin pre-creates a fixed mapping before first import.

The 4 fixed MG2 output elements

MG2trendEst · MG2adjEstim MG2forecast · MG2wpeEffct

Analogous to CHAP’s 5 quantile slots — a curated small set. Step 4 is a placeholder.

Discussion point: What should Step 4 actually write? This is an open design question.

Walk through the four steps. Emphasize the contrast on data element creation: CHAP requires admin pre-configuration; MG2 infers everything from the loaded formula. That means it works immediately for any dataset but raises a different question — if you create data elements dynamically, how does anyone else know what they mean? The 4 fixed output UIDs are the one concession to pre-configuration. Step 4 being a placeholder is honest — we built the infrastructure but we haven’t decided what model outputs to write and at what granularity. That’s partly why we’re having this conversation.

Open Questions — We Want Your Input

Technical

  • Step 4 granularity: facility-level or district-level? All months or forecast horizon only? One value per type or full quantile bands?

  • Push to source instance: is there a safe path? Custom namespace? Attribute option combo to separate model outputs from program data?

  • Provenance: if the analyst re-runs with different parameters, old values are overwritten silently. Acceptable?

  • Production hosting: a separate output DHIS2 instance needs infrastructure — what is the right companion deployment pattern?

Design philosophy

  • Should external analytics tools standardize on a small curated output set (CHAP style) — or is that the wrong constraint for health data modeling?

  • Is there a DHIS2 metadata pattern for provenance — who ran what model with what parameters, and when?

  • Is a shared standard for external-analytics-to-DHIS2 output routing worth proposing to the community?

Has anyone solved the bottom-right quadrant? Rich, diverse model outputs — visible in DHIS2 dashboards — at scale. If so, we want to learn from you. If not, let’s design it together.

This is the invitation. Read out the questions. Give the audience space to respond — this slide should take 10-15 minutes. The goal is to find out (1) whether anyone has a pattern we haven’t thought of, particularly around provenance and attribute option combos, and (2) whether there is appetite for a community standard or working group.
